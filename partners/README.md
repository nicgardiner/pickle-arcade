# Pickle Arcade partner program

Outside developers whose games are published in Pickle Arcade maintain those games themselves, in
their own fork of this repo, and send changes back as GitHub pull requests. Nic reviews and merges;
the change ships with the next launcher release and, from `main`, on the website.

Each partner owns one folder: `partners/<partner>/`. Everything a partner's game needs — its source,
its integration layer, its games.json entry, its covers — lives there. The root game file, the root
`covers/` files and the game's `games.json` entry are **generated** from that folder by
`partners/build.mjs`, so they are never edited by hand.

| Path | What it is |
|---|---|
| `partners/<partner>/README.md` | your contract: your games, what you may change, the rules CI enforces |
| `partners/<partner>/<gameId>/` | one folder per game (layout in your README) |
| `partners/build.mjs` | the generator: folder → root game file, `covers/`, `games.json` |
| `partners/onboarder/SKILL.md` | how to prepare a new game for onboarding |
| `partners/partners.json` | maps a partner folder to its GitHub login(s) |
| `partners/check-pr.mjs` | the CI scope check run on every partner PR |

The whole `partners/` tree is excluded from app builds; only the generated outputs ship.

## One-time setup

You need Git, Node.js (LTS) and the GitHub CLI (`gh`).

1. **GitHub account.** Send Nic your login; he adds it to `partners/partners.json`. Until then CI
   treats your PRs as an unknown author.
2. **Fork** https://github.com/nicgardiner/pickle-arcade on GitHub (Fork button, keep the name).
3. **Clone your fork** and install:
   ```bash
   git clone https://github.com/<your-login>/pickle-arcade.git
   cd pickle-arcade
   npm install
   ```
4. **Add the upstream remote** (Nic's repo), so you can pull his changes:
   ```bash
   git remote add upstream https://github.com/nicgardiner/pickle-arcade.git
   ```
5. **Sign in the GitHub CLI** (the launcher uses it to open pull requests):
   ```bash
   gh auth login
   ```
6. **Turn on partner mode.** Create `_dev/partner.json` (the `_dev/` folder is gitignored, so this
   file never leaves your machine):
   ```json
   { "partner": "jertal", "github": "<your-login>", "upstream": "nicgardiner/pickle-arcade" }
   ```
   `partner` is your folder name under `partners/`.
7. **Point your Claude at the rules.** Create `CLAUDE.md` in the repo root (it is gitignored, so it
   stays yours) containing:
   ```markdown
   This is a Pickle Arcade partner checkout. Before any work, read partners/README.md and
   partners/<partner>/README.md and follow them. Only change files inside partners/<partner>/;
   root files of my games are generated by `node partners/build.mjs <partner>`.
   To onboard a new game, follow partners/onboarder/SKILL.md.
   ```
8. **Run the launcher from source:**
   ```bash
   npm start
   ```

### What partner mode changes
When `_dev/partner.json` exists and the app runs from source:
- It uses its own profile (`Pickle Arcade Partner`), so test runs never touch the stats or
  achievements of an installed copy of Pickle Arcade.
- Owner-only features are off.
- Leaderboard posts are no-ops — test runs never reach the live boards.
- The Dev Shelf gets a **Published** tab listing your games, with **Build & play**, **Folder**,
  **DEVLOG** and **Request update**. A game that isn't in Nic's library yet shows as a **Draft** with
  **Send onboarding request** instead; Black Knight carries an **External release** badge (its flow
  is in its own README).
- Your own projects in `_dev/` show on the Dev Shelf with **Submit for onboarding**: name the game,
  optionally attach a cover, and copy the prompt it gives you to your Claude.

## The loop: edit → build & play → request update

1. **Edit** files inside `partners/<partner>/<gameId>/` only (usually `source/` and, when the
   integration needs it, `patch.mjs`). Write anything Nic should know into `REQUEST-NOTES.md` in the
   same folder.
2. **Build & play.** Either click **Build & play** on the game in the Published tab, or run:
   ```bash
   node partners/build.mjs <partner> <gameId>
   npm test
   ```
   then launch the game from the library. `npm test` must pass before you send anything.
3. **Request update.** Click **Request update** on the game. The form is prefilled from
   `REQUEST-NOTES.md`; it checks the build is current (`node partners/build.mjs <partner> --check`),
   commits that game's folder and its generated outputs (nothing else) to a new branch named
   `partner/<gameId>-<yyyymmdd-hhmm>`, pushes it to **your fork**, and opens a pull request against
   `nicgardiner/pickle-arcade:main` titled `[<partner>] Update <Title>` (`Onboard` for a draft).
   Afterwards those files go back to your last commit on your current branch — the changes live on the
   new branch until Nic merges them (`git checkout <that branch>` to keep working on them first), and
   your fork syncs cleanly once he has.

The PR body has four sections (the same headings as `.github/pull_request_template.md`):

| Section | What goes in it |
|---|---|
| `## What changed` | what the player will notice |
| `## Notes & extras` | anything outside your folder you are asking for (see below), and questions |
| `## Claude's notes` | your Claude's notes from `REQUEST-NOTES.md` |
| `## Onboarding` | only for a new game: the onboarding preview |

**Doing it by hand** (if the launcher is unavailable): create the branch, commit your folder and the
generated outputs, push to `origin` (your fork), then
`gh pr create --repo nicgardiner/pickle-arcade --base main` with the title and sections above.

## How review works

1. **CI scope check** (`.github/workflows/partner-check.yml`) runs on every PR from a mapped login:
   - every changed path must be under `partners/<partner>/` or be one of your generated outputs
     (the root file of each of your non-external games, the `covers/` files copied from your covers
     folders, and your own entries in `games.json`);
   - `node partners/build.mjs <partner> --check` must pass on your branch, i.e. the generated
     outputs you committed are exactly what your folder produces;
   - every `games.json` entry that is not yours must be unchanged (and its other top-level keys too);
   - a new game may not reuse an existing id or overwrite an existing file, and a published game's
     folder may not be deleted (removing a game is Nic's call).

   It also lists, as warnings for Nic to look at (they do not fail the PR), anything NEW in files you
   changed under your folder: `electronAPI`, `ipcRenderer`, `require(`, `child_process`, `process.`,
   `eval(`, `new Function`, new http(s) hosts, and localStorage keys outside `gl_<gameId>_*`.
   A separate **library** job runs `npm test`, which must also pass. On an onboarding PR it can be red
   until Nic adds what only he can (a `preload.js` allowlist entry, a `vendor/` file); the job summary
   says so.
2. **Nic reviews and merges.** He may ask for changes in the PR.
3. **It ships with the next release.** Merged changes reach players in the next launcher update, and
   on the website (https://nicgardiner.github.io/pickle-arcade/) once `main` redeploys.

## Out of bounds, and how to ask anyway

You can't change anything outside your folder: the launcher (`main.js`, `renderer.js`, `preload.js`,
`index.html`, `style.css`, …), the SDKs, `vendor/`, other games, CI, or other partners' entries. A PR
that touches any of it fails the scope check.

Things that need a change outside your folder, so only Nic can make them:
- a **global leaderboard** for a game (the game id goes in `LEADERBOARD_GAMES` in `preload.js`)
- **online multiplayer through the shared LobbySDK** (the game id goes in `ONLINE_MULTIPLAYER_GAMES`
  in `preload.js`)
- a new engine version or addon in `vendor/`
- a launcher tweak, a new tag, a new global achievement

Ask for these in the PR's **Notes & extras** section (or put the request in `REQUEST-NOTES.md` so it
lands there). Say what you need and why; Nic makes the change on his side.

## Keeping your fork in sync

Before starting new work, bring your fork up to date with Nic's `main`:

```bash
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
```

(`gh repo sync <your-login>/pickle-arcade` does the same from the GitHub side.) Then run
`npm install` again if `package.json` changed, and rebuild your games
(`node partners/build.mjs <partner>`) before testing. Start each update from a fresh, synced `main`.
